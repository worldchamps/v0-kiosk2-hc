# 키오스크 미수금 결제: 장비별 키 대신 기존 장비 인증 사용

작성 2026-10-20. 이전 계획 `2026-10-20-키오스크-미수금-결제.md`(PMS)와 키오스크 `docs/plans/2026-10-20-현장결제-미수금.md`의 인증 부분만 바꾼다. 같은 문서를 두 저장소에 둔다.

## 왜

- 설치된 키오스크는 `.env.local`을 장비 등록 때 한 번만 읽어 암호화 설정에 저장한다(`electron/device-setup.js`). 장비마다 `PMS_KIOSK_KEY`를 넣으려면 8대를 다시 등록해야 한다.
- PMS에 `PMS_KIOSK_KEYS`를 넣는 Vercel 설정도 하지 않기로 했다.
- 키를 코드에 하드코딩하면 GitHub와 설치파일(.exe)에 노출된다. 그래서 하지 않는다.
- 키오스크는 이미 장비마다 `beachstay-kiosk-updates` Firebase 익명 로그인을 갖고 있고, `bindings/{장비ID}.uid`로 장비와 묶여 있다(`electron/firebase-updates.js`, `ops/updates/database.rules.json`). 이 로그인을 PMS 인증에 쓴다.

## 인증 방식

키오스크 → PMS 요청 헤더:
- `Authorization: Bearer <beachstay-kiosk-updates Firebase ID 토큰>`
- `X-PMS-Kiosk-Device: <장비ID>` (`KIOSK_DEVICE_ID`, 예: `property1-kiosk-01`)

PMS 검증 순서(`lib/pms-kiosk-device.ts` 새 파일, 비동기):
1. 장비ID 형식 `^[A-Za-z0-9_-]{1,200}$`, 토큰 길이 상한(4096) 확인.
2. firebase-admin 보조 앱(`initializeApp({ projectId: "beachstay-kiosk-updates" }, "kiosk-updates")`)의 `getAuth().verifyIdToken(token)`으로 서명·만료·aud/iss를 검증한다. 자격증명은 필요 없다(Google 공개키로 검증). 기존 kiosk-pms 앱과 섞지 않는다.
3. 검증한 토큰으로 `https://beachstay-kiosk-updates-default-rtdb.asia-southeast1.firebasedatabase.app/status/{장비ID}.json?auth=<토큰>`을 GET(5초 제한, redirect: "error"). DB 규칙상 이 읽기는 `bindings/{장비}.uid === 토큰 uid` 이고 `registry/{장비}.revoked === false`일 때만 200이다. 즉 장비 묶임과 폐기 여부를 한 번에 확인한다. 401/403이면 거절, 그 밖의 실패는 503.
4. 통과 결과를 메모리에 캐시한다: 키 `sha256(token)+장비ID`, 만료 `min(토큰 exp, 지금+5분)`. 장비 폐기(`kiosk-deploy revoke`)는 최대 5분 뒤 반영된다. 캐시 크기 상한 100개.
- 프로젝트 ID와 DB 주소는 비밀이 아니므로 상수로 둔다(키오스크 `electron/update-cloud.json`과 같은 값).
- 업데이트 DB의 규칙, kiosk-pms 규칙은 바꾸지 않는다.

### 시범 장비 제한 (PMS)
- `lib/pms-kiosk-device.ts`에 `KIOSK_COLLECTION_DEVICES = ["property1-kiosk-01"]` 상수. 인증은 통과했지만 목록에 없는 장비는 `GET /api/kiosk/balance`에 `200 { enabled: false }`를 준다(collections는 404). 운영자가 시범 장비를 늘리면 이 목록만 고친다. 환경변수로 만들지 않는다.

## PMS 변경 (v0-PMS-l8, origin/main a6ff388 기준)

- `lib/pms-auth.ts`의 `getPmsKioskId`와 `PMS_KIOSK_KEYS` 처리 삭제.
- `lib/pms-auth-server.ts` kiosk scope: 경로·메서드 확인 후 `await verifyKioskDevice(request.headers)`. 실패는 지금처럼 404, Origin 헤더가 있으면 403, 검증 서버 오류는 503(no-store). 일반 경로에서 `X-PMS-Kiosk-Device` 헤더가 있으면 404(기존 `getPmsKioskId` 차단을 대체, 동기 확인만).
- `app/api/kiosk/collections/route.ts`: `input.kioskId`를 검증된 장비ID와 비교(지금의 `getPmsKioskId` 비교 대체). 시범 목록에 없으면 404.
- `app/api/kiosk/balance/route.ts`: 시범 목록에 없으면 `200 { enabled: false, reservationId }`.
- 문서: `docs/PMS_STAFF_LOGIN.md` 키오스크 인증 절, 이전 계획 문서의 `PMS_KIOSK_KEYS` 언급에 "대체됨" 한 줄.
- 테스트(`tests/kiosk-collections.test.mts`): `verifyIdToken`과 fetch를 목으로 바꿔 다음을 확인한다.
  - 정상 → 통과, 캐시 재사용(두 번째 호출에 fetch 없음)
  - 서명 실패 → 404
  - status 읽기 401/403 → 404 (폐기·다른 장비 uid)
  - status 읽기 500/타임아웃 → 503
  - 헤더 장비ID ≠ body kioskId → 403
  - 시범 목록 밖 → balance `enabled:false`, collections 404
  - Origin 헤더 → 403
  - 일반 API에 `X-PMS-Kiosk-Device` → 404
- 실데이터·Vercel 설정 쓰기 금지. `npm test`, `npm run build` 통과.

## 키오스크 변경 (v0-kiosk2-hc, origin/main 1eccece 기준)

- `electron/firebase-updates.js`: `createDeviceConnection`이 `idToken()`(= 기존 `authenticate`)을 반환한다. `authenticate`에 진행 중 Promise 공유를 넣어, 업데이트 폴링과 결제 요청이 동시에 토큰을 갱신해 `persist`가 겹치지 않게 한다.
- `electron/bootstrap.js`: 연결을 한 번만 만들고 `pollStatus`와 함께 `global.kioskDeviceIdToken = connection.idToken`을 둔다. Next 서버는 같은 프로세스(`electron/main.js`의 `require("next")`)라 API 라우트에서 `globalThis.kioskDeviceIdToken`으로 부를 수 있다. 개발 모드(미패키지)에는 없으므로 기능이 꺼진다.
- `lib/pms-kiosk.ts`:
  - `PMS_BASE_URL` 기본값 `https://v0-pms-seven.vercel.app`(환경변수가 있으면 우선).
  - `PMS_KIOSK_KEY` 삭제. 설정 조건은 `KIOSK_DEVICE_ID` 형식이 맞고 `globalThis.kioskDeviceIdToken`이 함수일 것.
  - `pmsFetch`는 토큰을 받아(토큰 획득 시간도 기존 제한 시간 안에서 계산) 위 두 헤더를 넣는다. 토큰 획득 실패는 PMS 호출 실패와 같게 처리한다.
- `app/api/reservation-balance/route.ts`:
  - PMS가 404를 주거나 `{ enabled: false }`를 주면 `{ configured: false }`로 답한다. 이것은 PMS가 아직 Promote되지 않았거나 시범 장비가 아닌 경우다. 이때 지금처럼 기존 체크인 흐름을 탄다. 직접 예약 체크인이 막히면 안 된다.
  - 그 밖의 실패는 지금처럼 503.
- `app/api/reservation-collection/route.ts`: 같은 헤더 사용. 응답 처리 규칙은 그대로.
- `ENV_SETUP_GUIDE.md`, `docs/PAYMENT_RECOVERY.md`: `PMS_KIOSK_KEY` 설정 절을 "장비 인증 자동 사용, PMS 시범 장비 목록에서 켬"으로 바꾼다.
- 테스트:
  - 토큰 함수가 없으면 `configured:false`
  - 헤더 두 개가 실림
  - PMS 404 / `enabled:false` → `configured:false`
  - PMS 500 → 503
  - 동시 `idToken()` 호출이 갱신을 한 번만 함
  - 기존 장애 주입 테스트 유지
- `npm test`, `npm run build` 통과. 버전 올림·설치파일 빌드·게시·장비 요청은 하지 않는다(별도 승인).

## 반영 순서 (각 단계 사용자 승인)

1. PMS main push → Preview 확인 → 사용자가 Promote.
2. 키오스크 1.3.53 빌드·게시 → 장비 업데이트 요청. PMS가 먼저 반영되지 않아도 키오스크는 기존 흐름으로 동작한다(404 → configured:false).
3. 시범 장비(`property1-kiosk-01`)에서 카드·현금 소액 실결제 시험.
4. 이상 없으면 PMS `KIOSK_COLLECTION_DEVICES`에 장비 추가.

## 두 에이전트 간 계약

헤더 이름, `enabled:false` 응답, 404 의미는 위 그대로 고정한다. 바꿀 필요가 생기면 구현 전에 상대 작업자에게 묻는다.

- 작성: Claude(계획). 구현: Codex. 기준 커밋 `origin/main` = `8326ff4`.
- 목표: PMS(ChatGPT 비서·직원 수동 예약)에서 미수로 만든 직접·전화·현장예약 손님이 키오스크에서 이름·QR로 체크인할 때, 남은 금액(예약금액 − PMS 수금 합계)을 카드·현금으로 받고, PMS 수금 기록을 남긴 뒤 기존 체크인 안내로 이어 간다.

## 2. 확정 계약 (PMS 담당과 합의)

### 환경변수 (키오스크 PC `.env.local`, Git에 넣지 않음)

- `PMS_BASE_URL` — 예: `https://<PMS 도메인>` (끝 `/` 없이)
- `PMS_KIOSK_KEY` — 장비별 키, 32자 이상. PMS는 `PMS_KIOSK_KEYS="kioskId1:key1,..."`로 키→kioskId를 정한다.
- `KIOSK_DEVICE_ID` — 기존 값. 요청 본문의 `kioskId`로 서버가 넣는다(클라이언트 값 사용 금지). 키와 짝이 다르면 PMS가 403.
- `PMS_BASE_URL` 또는 `PMS_KIOSK_KEY`가 없으면 이 기능은 꺼진 것으로 보고 **현재와 똑같이** 체크인한다(점진 배포용). 서버 로그에 한 번 경고.

### GET `{PMS_BASE_URL}/api/kiosk/balance?reservationId=<id>`

- 헤더 `Authorization: Bearer <PMS_KIOSK_KEY>`, 타임아웃 8초, `redirect: "error"`.
- 응답 `{ status, reservationId, guestName, place, roomNumber, channel, checkInDate, price, collected, remaining, payable, reason? }`
- `payable=true` 조건(PMS 판단): 직접 채널(D열이 `현장`으로 시작·`직접예약`으로 시작·정확히 `전화예약`), 취소 아님, L열 빈 값, 체크인 날짜 ≤ 오늘(KST), `remaining>0`, 그리고 미해결 키오스크 결제가 없음.
- `reason="kiosk_payment_unresolved"`: 같은 예약에 recorded가 아닌 PMS 수금 클레임(같은 expectedCollected) 또는 미처리 `collection_unrecorded` 사고가 있음. 키오스크는 결제도 체크인도 하지 않는다.
- 키오스크 현장 판매 행(D=`키오스크`)과 플랫폼 예약은 `payable=false`. 채널 판단은 PMS가 하고 키오스크는 `payable`/`remaining`만 믿는다.

### POST `{PMS_BASE_URL}/api/kiosk/collections`

- 본문 `{ reservationId, expectedCollected, amount, method: "카드"|"현금", paymentKey, kioskId, paidAt }`
  - `expectedCollected` = balance의 `collected`(필수). `amount` = balance의 `remaining`과 정확히 같아야 한다(부분 결제 없음, 다르면 400).
  - `paymentKey`: 카드는 토스 프론트 `paymentKey`, 현금은 키오스크가 결제 시작 전에 만든 `cash-<uuid>`.
  - `paidAt`: ISO 문자열. 카드는 승인 `timestamp`, 현금은 투입 완료 시각. 재전송에도 같은 값.
- PMS 처리 순서: `kiosk_collection_claims/{sha256(paymentKey)}` 클레임을 **먼저** 잡는다 → 같은 키·같은 reservationId·amount면 `duplicate`(기록된 amount, recordedAt 포함), 다르면 `conflict`(409) → 클레임 확보 후 stale/not_payable 검사 → 기록. 기록 실패 시 클레임은 `failed`로 남아 같은 키 재전송이 다시 시도된다.
- 결과 `status`: `recorded` | `duplicate` | `stale` | `not_payable` | `conflict` | `error`.
- 키오스크 성공 판정: HTTP 2xx이고 `status`가 `recorded` 또는 `duplicate`이며 `reservationId`가 일치할 때만.

## 3. 화면 흐름

```
[예약 체크인] 이름/QR 조회 ──(기존)──> [예약 상세 ReservationDetails]
        │ "체크인" 버튼 → handleCheckIn()
        ▼
 (1) 카드 발급기 사전 점검 checkCardBeforePayment (기존, 실패 시 5초 후 첫 화면)
        ▼
 (2) GET /api/reservation-balance  (8초)
        ├─ 기능 꺼짐(env 없음) ───────────────────────> (5) 기존 체크인
        ├─ 실패 + D열 직접채널 ──> "결제 확인 불가, 010-5126-4644" → 5초 후 첫 화면
        ├─ 실패 + 그 외 채널 ─────────────────────────> (5) 기존 체크인
        ├─ reason=kiosk_payment_unresolved ──> "이전 결제 확인 중, 010-5126-4644" → 5초 후 첫 화면
        ├─ payable=false ─────────────────────────────> (5) 기존 체크인
        └─ payable=true, remaining>0
                ▼
 (3) [결제 reservationPayment] PaymentScreen(card=remaining, cash=remaining 또는 0)
        ├─ 취소/이전 화면 → 결제 세션 정리 → 첫 화면
        ├─ 60초 무입력(현금 0원·카드 진행 아님) → 세션 정리 → 첫 화면
        ├─ 결제 장애(recoveryRequired) → 5초 후 첫 화면(기존 자동 보관)
        └─ 결제 완료(CompletedPayment)
                ▼
 (4) "결제 기록 중" 화면: pendingBooking(kind=collection) 저장 → POST /api/reservation-collection
        최대 3회, 회당 10초, 총 30초
        ├─ recorded/duplicate → completePayment()(잠금 해제)
        └─ 그 외/불확실 → pendingBooking 유지(첫 화면에서 재확인 후 사고 보관)
                ▼
 (5) POST /api/check-in (기존, 결제 후에는 카드 사전 점검 생략) → 카드 발급 → [체크인 완료]
```

- 결제가 증명되면(카드 승인 증빙, 현금 필요액 도달) 수금 기록 결과와 상관없이 체크인을 진행한다. 입실 허용 여부는 기존 `/api/check-in`이 판단한다.
- 같은 이름 여러 건은 기존 목록 화면에서 고른 예약 하나에 대해서만 (2)를 호출한다. 변경 없음.

## 4. 바꿀 파일

### 새 파일

1. `lib/pms-kiosk.ts` (서버 전용)
   - `pmsKioskConfig()` → `{ baseUrl, key, kioskId } | null` (셋 중 하나라도 없으면 null; `PMS_KIOSK_KEY` 32자 미만도 null).
   - `pmsFetch(path, init, timeoutMs)` — `Authorization: Bearer`, `redirect: "error"`, `AbortSignal.timeout`.
   - `requiresPmsBalance(bookingPlatform: string)` — `/^현장/`·`/^직접예약/`·`=== "전화예약"` (trim 후). 클라이언트에서도 쓰므로 이 함수만 별도 `lib/reservation-collection.ts`에 둬도 된다.
2. `app/api/reservation-balance/route.ts` — `GET ?reservationId=`
   - reservationId 검증(문자열, 1~200자). 설정 없으면 `200 { configured: false }`.
   - PMS 호출 8초. 응답 검증: `reservationId` 일치, `price`·`collected`·`remaining`이 0 이상 safe integer, `payable` boolean. 실패·형식 오류는 `503 { error }`.
   - 성공 시 `200 { configured: true, payable, remaining, collected, price, reason }`만 돌려준다(이름·전화 등은 넘기지 않는다).
3. `app/api/reservation-collection/route.ts` — `POST`
   - 본문 `{ requestId, reservationId, expectedCollected, amount, paidAt, payment: CompletedPayment }`.
   - 검증: amount·expectedCollected safe integer, amount>0; `payment.method`가 `CARD`면 `provider === "TOSS_FRONT"`이고 `requestId === payment.front.paymentKey`, `verifyTossFrontPaymentProof(payment.front, amount)` 통과; `CASH`면 `requestId`가 `/^cash-[0-9a-f-]{36}$/`.
   - 카드면 `claimPayment("toss_front", paymentKey, { reservationId, amount, purpose: "collection" })`. 이미 있으면 `getPaymentClaim` 값의 `reservationId`·`purpose`·`amount`가 같을 때만 계속(재전송), 다르면 `409 { status: "conflict" }`(PMS 호출 안 함). 이 claim은 현장판매 재사용 차단과 관리자 카드취소 도구 조회용이며 지우지 않는다.
   - PMS POST(10초): `{ reservationId, expectedCollected, amount, method: CARD→"카드"/CASH→"현금", paymentKey: requestId, kioskId, paidAt }`.
   - 반환: PMS의 `status`를 그대로 담아 `{ status, reservationId }`. 네트워크 오류·타임아웃·5xx·형식 오류는 `{ status: "error" }`(HTTP 503). 설정 없음도 `{ status: "error" }`(결제 화면까지 왔다면 설정이 사라진 것이므로 사고로 남긴다).
4. `lib/reservation-collection.ts` (클라이언트 공용)
   - `submitCollection(body: string): Promise<string>` — `/api/reservation-collection` 1회 호출, `status` 문자열 반환(예외는 `"error"`).
   - `isCollectionRecorded(status)` — `recorded`/`duplicate`.
   - `cashCollectionAmount(remaining, cashBackend)` — `remaining % 1000 !== 0`이면 0, `cashBackend === "bac2400"`이고 `remaining % 10000 !== 0`이면 0, 아니면 remaining.

### 수정 파일

5. `contexts/payment-context.tsx`
   - `PendingBooking`에 `kind?: "collection"`, `lastStatus?: string` 추가. 저장본 검증에서 `kind`는 `undefined` 또는 `"collection"`만, `lastStatus`는 40자 이하 문자열만 허용.
   - 그 밖의 동작은 바꾸지 않는다(`startPayment`가 `pendingBooking` 있을 때 새 결제를 거부하는 기존 잠금을 그대로 쓴다).
6. `components/kiosk-layout.tsx`
   - 상태 추가: `collection: { reservationId, remaining, collected, cashAmount, requestId } | null`, 화면 `"reservationPayment"`, `"collectionRecording"`(“결제를 기록하고 있습니다. 화면을 끄거나 다시 결제하지 마세요.”).
   - `handleCheckIn(override, { paid = false } = {})`:
     - `!checkInPending && !paid`일 때 기존 카드 사전 점검 뒤 `/api/reservation-balance` 호출(8초 + 여유, 클라이언트 `AbortSignal.timeout(10000)`).
     - 분기는 3장 흐름도 그대로. 차단 분기는 `definitiveFailure = true`로 처리해 `checkInPending`을 켜지 않고, 기존 `cardPreflightFailed`와 같은 5초 후 첫 화면 복귀를 쓴다.
     - 결제 분기: `requestId = "cash-" + crypto.randomUUID()`(카드는 승인 후 paymentKey로 바뀐다), `cashAmount = cashCollectionAmount(remaining, (await getHardwareStatus()).cashBackend)`(조회 실패 시 0), `startPayment(remaining, { reservationId, roomNumber, guestName, purpose: "collection" })` 성공 시 `"reservationPayment"`로 이동하고 `false` 반환.
     - `paid=true`면 카드 사전 점검과 balance 조회를 건너뛰고 기존 `/api/check-in`부터 진행한다.
   - `"reservationPayment"` 화면: `<PaymentScreen cardAmount={remaining} cashAmount={cashAmount} title="남은 금액 결제" description="예약 체크인을 위해 남은 금액을 결제해주세요" …>`.
     - `onCancel`/`onUnavailable`: PaymentScreen이 이미 `cancelPayment()`를 끝낸 뒤 부르므로, `handleNavigate`(오래된 `paymentSession.isActive`로 막힘)를 쓰지 말고 첫 화면 리셋을 직접 하는 `goHome()`을 만든다(`setHomeSessionKey`, 화면·예약·`collection` 초기화). `onUnavailable`은 메시지를 `error`로 보여 준 뒤 5초 후 `goHome()`.
     - 결제 수단 선택 화면의 "이전 화면"은 `cancelPayment()`가 `true`일 때만 `goHome()`.
     - `useIdleTimer({ idleTime: 60000, enabled: currentScreen === "reservationPayment" })`: `acceptedAmount === 0 && !cardInFlight && !pendingBooking && !recoveryRequired`일 때만 `cancelPayment()` 후 `goHome()`. 현금이 들어왔으면 기존 현장판매와 같이 화면을 유지한다(자동 반환 없음).
     - `paymentSession.recoveryRequired || storageError`가 생기면 5초 후 `goHome()`. 첫 화면의 기존 자동 보관이 처리한다.
   - `onPaymentComplete(payment)` → `handleCollectionComplete`:
     1. `requestId` = 카드면 `payment.front.paymentKey`, 현금이면 미리 만든 `cash-<uuid>`. `paidAt` = 카드 `new Date(front.timestamp).toISOString()`, 현금 `new Date().toISOString()`.
     2. `savePendingBooking({ kind: "collection", requestId, body: JSON.stringify({ requestId, reservationId, expectedCollected, amount: remaining, paidAt, payment }) })` 실패 시 중단(기존 저장 오류 경로).
     3. `"collectionRecording"` 화면에서 `submitCollection`을 최대 3회(실패 사이 2초) 호출. 매 결과를 `lastStatus`로 `savePendingBooking`에 갱신.
     4. `recorded`/`duplicate`면 `completePayment()`. 아니면 `pendingBooking`을 그대로 둔다(`requireRecovery` 호출 금지 — 장비 고장 보고가 나간다).
     5. 어느 쪽이든 `handleCheckIn(adminOverride, { paid: true })`.
   - 첫 화면 복귀 시 `pendingBooking`이 남아 있어도 `handleNavigate`의 기존 `paymentInterrupted` 조건으로 이동할 수 있다(변경 없음).
7. `components/on-site-reservation.tsx`
   - `submitPendingBooking`에서 `booking.kind === "collection"`이면 `/api/on-site-booking` 대신 `submitCollection(booking.body)` 1회:
     - `recorded`/`duplicate` → `completePayment()`(사고 없이 해제). 완료 화면·카드 발급은 하지 않는다.
     - 그 외 → `lastStatus` 갱신, `setBookingError("결제는 완료되었으나 수금 기록을 확인하지 못했습니다. 010-5126-4644")`. `finally`의 `setBookingChecked(true)`로 `PaymentRecoveryPanel`이 4초 뒤 자동 보관한다.
   - 기존 현장판매 분기는 바꾸지 않는다.
8. `electron/payment-recovery.js`
   - `automaticKind`: `session.pendingBooking` 이면 `kind === "collection"` → `'collection_unrecorded'`, 아니면 기존 `'booking_pending'`.
9. `electron/cash-incidents.js`
   - `verifyIncident` 허용 kind에 `'collection_unrecorded'` 추가.
   - 선택 필드 `collection` 검증: `kind === 'collection_unrecorded'`일 때만 필수, 그 외에는 없어야 함. `{ reservationId: 1~200자, amount: safe int ≥0, method: '카드'|'현금', paymentKey: 1~300자, pmsStatus: 0~40자 }` 외 필드 금지.
   - `incidentFromArchive`: `incidentKind === 'collection_unrecorded'`면 `session.pendingBooking.body`를 파싱해 `collection`을 채우고 `reason = "결제 완료·PMS 수금 기록 미확인 (" + lastStatus + ")"`, `requiredAmount = amount`. 현금이면 `receivedAmount` 등 기존 현금 필드 계산을 그대로 쓴다. body 파싱에 실패하면 빈 값을 채우지 말고 kind를 `'corrupt'`로 보낸다.
   - 전화번호·객실 비밀번호는 보내지 않는다(본문에 없음).
10. `docs/PAYMENT_RECOVERY.md` — 사고 종류 목록에 `collection_unrecorded` 한 줄 추가. `.env` 예시 문서(`ENV_SETUP_GUIDE.md`)에 `PMS_BASE_URL`, `PMS_KIOSK_KEY` 추가(값 없이).

바꾸지 않는 것: `payment-screen.tsx`, `toss-front-card-payment.tsx`, `/api/check-in`, `/api/reservations`, `/api/on-site-booking`, 지폐 장비 코드.

## 5. 장애 처리

| 상황 | 키오스크 동작 | 돈 | PMS |
|---|---|---|---|
| balance 실패, 직접채널 | 안내 후 5초 뒤 첫 화면, 체크인 안 함 | 받지 않음 | — |
| balance 실패, 그 외 | 기존 체크인 | 받지 않음 | — |
| `kiosk_payment_unresolved` | 안내 후 5초 뒤 첫 화면, 체크인 안 함 | 받지 않음 | 직원이 수금 기록·사고 처리하면 해제 |
| 결제 전 장비 준비 실패 | 기존 `onUnavailable` → 5초 뒤 첫 화면 | 받지 않음 | — |
| 결제 중 장애(현금 확인 불가, 카드 결과 불명) | 기존 `requireRecovery` → 5초 뒤 첫 화면 → 자동 보관(`cash`/`unknown_result`/`card_approval`) | 미확정 | 기존 결제 사고 |
| 결제 성공 + 기록 `recorded`/`duplicate` | 잠금 해제 → 체크인 | 받음 | 수금 기록됨 |
| 결제 성공 + 기록 `stale`/`not_payable`/`conflict` | 3회 시도 후 체크인 진행, 첫 화면에서 1회 재확인 후 `collection_unrecorded` 보관 | 받음 | 사고로 확인. 재결제는 balance가 막음 |
| 결제 성공 + 기록 결과 불확실(타임아웃·5xx·응답 유실) | 같은 본문 재전송(멱등) 최대 3회, 이후 위와 같음 | 받음 | 클레임 `failed`/진행 중이면 balance가 막음 |
| 기록 중 앱 종료·재시작 | 재시작 후 `pendingBooking`(collection) 복원 → 첫 화면이 1회 재전송 → 실패 시 자동 보관 | 받음 | 위와 같음 |
| 결제·기록 후 체크인 실패 | 기존 `checkInPending`(5초 뒤 첫 화면). 재조회 시 기록됐으면 remaining=0이라 결제 없이 체크인, 미기록이면 `kiosk_payment_unresolved`로 막힘 | 받음 | — |
| 현금 거스름돈 일부 미지급 | 기존 `change_owed` 사고, 체크인 진행. PMS 기록 amount는 remaining | 받음 | 기존 잔돈 사고 |

원칙: 자동 카드취소·자동 현금 반환·같은 예약 재결제는 하지 않는다. 고객 화면은 어떤 경로든 관리자 입력 없이 5초(장애) 또는 60초(무입력) 안에 첫 화면으로 돌아간다. 사람 판단(환불·수금 정정)은 PMS 결제 사고 화면에서 한다.

## 6. 장애 주입 테스트 (`tests/reservation-collection.test.mts`, `tests/cash-incident-route.test.cjs` 확장)

기존 테스트처럼 `ts.transpileModule` + 가짜 `require`로 라우트를 실행하고, 가짜 `fetch`로 PMS를 흉내 낸다. 실제 PMS·Sheets·Firebase·장비에 쓰지 않는다.

1. balance 라우트: env 없음 → `configured:false`; PMS 타임아웃·500·형식 오류(reservationId 불일치, 음수, 문자열 금액) → 503; 정상 → 이름·전화가 응답에 없음; `Authorization` 헤더와 `redirect:"error"` 확인.
2. `requiresPmsBalance`: `직접예약`, `직접예약(카톡)`, `전화예약`, `현장예약(직원)` → true; `전화예약 취소`, `키오스크`, `야놀자`, 빈 값 → false.
3. `cashCollectionAmount`: 37,500 → 0; bac2400 + 45,000 → 0; bac2400 + 50,000 → 50,000; oneplus + 37,000 → 37,000.
4. collection 라우트 카드: 서명 위조·금액 불일치 → 400, PMS 호출 0회; 첫 claim 성공 후 PMS 응답 유실(타임아웃) → `error`; 같은 본문 재전송 → claim 재사용, PMS `duplicate` → 성공; 같은 paymentKey 다른 reservationId → `conflict`, PMS 호출 0회.
5. collection 라우트 현금: requestId 형식 오류 → 400; PMS `stale`/`not_payable` 그대로 전달; `kioskId`는 env 값이며 본문 값 무시.
6. 키오스크 흐름(상태 함수 단위 또는 `kiosk-ui-recovery.test.cjs` 방식 소스 검사): 기록 3회 실패 후에도 `handleCheckIn(..., { paid: true })` 호출, `requireRecovery` 미호출, `pendingBooking.kind === "collection"` 유지.
7. `on-site-reservation`: collection `pendingBooking` 복원 시 `/api/on-site-booking`을 호출하지 않고 `/api/reservation-collection`만 호출; `duplicate`면 `completePayment`; `error`면 `bookingChecked` → 자동 보관.
8. `payment-recovery.automaticKind`: collection → `collection_unrecorded`, 기존 pendingBooking → `booking_pending`.
9. `cash-incidents`: `collection_unrecorded` + 올바른 `collection` 통과; `collection` 누락·추가 필드·다른 kind에 `collection` → 거절; `incidentFromArchive`가 reservationId·paymentKey·lastStatus를 채우고 전화번호를 넣지 않음; body 파싱 실패 → `corrupt`.
10. 무인 복귀: 결제 화면 60초 무입력(현금 0원) → `cancelPayment` 후 첫 화면; 현금 투입 후 무입력 → 화면 유지; `recoveryRequired` 발생 → 5초 후 첫 화면; balance 차단 → 5초 후 첫 화면.
11. 이중결제: `pendingBooking`(collection) 있는 상태에서 다른 예약 결제 시작 → `startPayment` false.

수동 확인(실기기, 운영자 승인 후 1대): PMS 테스트 예약(승인된 안전한 테스트 예약)으로 카드 1건·현금 1건, PMS 수금 칸 메모 `키오스크 <kioskId> · <paymentKey>` 확인, PMS 끊고 결제 후 `collection_unrecorded` 사고와 재조회 차단 확인.

## 7. 구현·릴리스 메모

- 한 요구사항 = 한 커밋. `npm.cmd run build`(테스트 포함) 통과 후 커밋.
- 배포 전 운영자 작업(문서만, Codex는 하지 않음): 장비별 `PMS_KIOSK_KEY` 생성(32자 이상), PMS `PMS_KIOSK_KEYS`에 `KIOSK_DEVICE_ID:키` 등록, 각 키오스크 `.env.local`에 `PMS_BASE_URL`, `PMS_KIOSK_KEY` 추가. 키는 저장소·채팅에 남기지 않는다.
- env가 없는 장비는 기능이 꺼진 채 현재와 같이 동작한다. 따라서 설치본을 먼저 깔고 env는 장비별로 켤 수 있다.
- PMS 쪽 배포(balance·collections·사고 kind 라벨·`kiosk_payment_unresolved` 판정)가 먼저 운영에 있어야 env를 켠다.
- 릴리스는 같은 버전의 ia32·x64를 함께 `npm.cmd run electron:build:all`로 준비·검증한다. 게시(`kiosk:release`)와 장비 배포는 운영자 승인 후, 지정한 키오스크 1대 카나리아 + 실제 결제 확인 뒤 나머지에 한다.

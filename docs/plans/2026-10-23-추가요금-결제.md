# 예약 추가요금 키오스크 결제 (2026-10-23)

- PMS 계획: `v0-PMS-l8/docs/plans/2026-10-23-추가요금-키오스크결제.md`.
- 기존 흐름: [현장결제·미수금 계획](2026-10-20-현장결제-미수금.md). 플랫폼 예약도 추가요금 미수가 있으면 PMS가 `payable: true`를 반환할 수 있다.

## Balance 계약

`GET /api/kiosk/balance`의 기존 필드 `status, reservationId, guestName, place, roomNumber, channel, checkInDate, price, collected, remaining, payable, reason?`는 유지한다.

- `price`: 예약 F열 가격 그대로. 플랫폼 예약이면 플랫폼 결제액이며 키오스크 결제액으로 사용하지 않는다.
- `due?`: 받을 총액(0 이상 안전 정수 원). 직접 예약은 `price + 추가요금`, 플랫폼 예약은 추가요금만이다.
- `charges?`: `{ item: string, amount: number }[]`. 최대 20개, `item`은 1~20자 문자열, `amount`는 양의 안전 정수 원이다. 메모는 포함하지 않는다. 바베큐·인원추가·얼리체크인·레이트체크아웃·기타 등의 항목을 표시한다.
- 키오스크 `/api/reservation-balance`는 두 필드를 검증해 전달한다. `charges`가 없으면 `[]`, `due`가 없으면 응답에서도 생략한다. 형식 오류는 기존과 같은 HTTP 503이다. 기존 개인정보 제외 및 미해결 결제 차단은 유지한다.

## 화면·결제

- `charges`가 있으면 “추가요금 결제” 제목과 항목별 금액, “결제할 금액”(`remaining`)을 표시한다. 빈 배열이면 기존 화면을 유지한다.
- 모든 예약의 잔액을 조회하고 `payable && remaining > 0`일 때 기존 결제로 연결한다. 결제·수금 기록 금액은 항상 `remaining` 전액이며 분할·항목 선택은 없다.
- `requiresPmsBalance`와 조회 실패 정책은 그대로다. 직접 예약은 차단·5초 후 첫 화면 복귀, 플랫폼 예약은 기존 체크인을 진행한다. 결제 잠금·기록·복구 흐름도 유지한다.
- 가짜 PMS·장비로 정상 전달, 잘못된 필드 거절, 구 응답 호환, 플랫폼·직접 예약의 표시와 전액 수금 기록을 검증한다.

버전 변경, 출시 준비, 배포·업데이트, Firebase 실데이터 쓰기 및 `.env` 생성은 이 작업에 포함하지 않는다.

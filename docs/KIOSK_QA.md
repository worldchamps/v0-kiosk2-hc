# 키오스크 QA와 운영 승인 기준

코드가 빌드된 것, 화면이 작동한 것, 결제·장비·현장 업데이트가 검증된 것은 서로 다르다.
테스트 통과만으로 무인 영업이나 현장 업데이트를 승인하지 않는다.

## 변경마다 실행할 검사

저장소 루트에서 실행한다. 테스트는 모의 전송/메모리 DB를 사용하며 운영 예약·결제·장비를 변경하지 않는다.

```powershell
npm.cmd run test:qa
npm.cmd run typecheck
npm.cmd run test:toss-front
npm.cmd run build
npm.cmd audit --omit=dev
npm.cmd audit
git diff --check
```

- `test:qa`는 `tests/*.test.cjs`와 `tests/*.test.mts`를 자동 수집한다. 개별 검사 60초, 전체 실행 180초 제한을 적용한다.
- `build`와 설치파일 빌드 래퍼는 같은 전체 회귀 검사를 필수로 실행한다. 검사 실패 시 빌드를 중단한다.
- Next.js의 타입 검사 생략을 제거했다. 린트 구성은 아직 없으므로 lint 통과를 보고하지 않는다.
- 대실·숙박 정상 흐름뿐 아니라 돌아가기, 다른 객실 선택, 품절, 조회 실패, 중복 클릭, 응답 지연·유실, 미확정 결제, 재시작 복구를 검사한다.
- API 검사는 실제 라우트와 저장 로직에 가짜 Firebase/Sheets 전송을 연결한다. 프로덕션 Firebase 동시성이나 실장비의 검증을 대체하지 않는다.
- 설치파일 게시에는 별도로 동일 새 버전의 ia32/x64 빌드와 각 패키지 검증이 필요하다. 이미 게시한 버전은 덮어쓰지 않는다.
- Python 장비 계약도 설치파일에 사용할 각 아키텍처의 Python으로 `python tests/hardware-server-contract.py`를 실행한다. 실제 시리얼 장비 대신 모의 전송과 임시 loopback WebSocket을 사용한다. 설치파일 빌드 래퍼가 이 검사를 필수 실행한다.
- 의존성 검사 실패는 기능 검사와 별도 미해결 항목이다. Electron은 개발 의존성으로 선언되어도 설치파일에 포함되므로 `--omit=dev` 검사만으로 보안 검증을 마치지 않는다. 자동 `audit fix --force`나 호환성 미검증 주버전 변경을 하지 않는다.

## 비현장 확장 검사와 보안 경계

- 실제 API handler를 모의 저장소·결제 응답과 연결해 잘못된 요청, 다른 동 요금, 중복·유실·오염 응답을 검사한다. 객실 조회 단계에서는 비밀번호를 공개하지 않는다.
- 정상 완료 응답의 비밀번호가 빈 문자열이면 기존 계약대로 예약은 확정하되 관리자 문의로 안내한다. 선택 전 객실 정보의 비밀번호로 대체하지 않는다.
- 설치형 로컬 HTTP 서버는 허용한 loopback Host, 동일 Origin, JSON 변경 요청만 받는다. Python 장비 WebSocket은 Origin 없는 native 클라이언트만 받는다. 같은 PC의 임의 native 프로그램까지 인증하는 기능은 아니며, 직접 실행하는 `next dev`/`next start`에는 설치형 서버의 HTTP 가드가 없다.
- 업데이트 이력이 손상되면 원본을 보존하고 자동 설치를 중단한다. 일반 키오스크 이용은 유지하되 업데이트는 관리자 확인이 필요하다.
- BAC-2400은 동시 지급과 이전 응답을 새 지급 성공으로 오인하는 것을 막는다. 현재 지급의 수량·상태 증거가 불충분하면 성공으로 처리하지 않는다. 실제 누적/회차별 카운터 규약과 부분 지급은 장비에서 별도로 검증한다.
- QA 설치파일은 별도 디렉터리·시험 버전·시험 공개키로 생성한다. NSIS 추출, PE 아키텍처, 내장 Python self-test, SerialPort와 Next 등 내장 모듈 로딩, loopback API 실행을 검사한다. 압축 해제와 실행 검사만으로 Windows 설치·제거·재부팅 업데이트 성공을 주장하지 않는다.

## 화면 수동 검사

운영 인증정보가 없는 loopback 미리보기에서 가상 객실을 사용한다. 모든 쓰기 API와 외부 네트워크·실장비 접근을 차단했는지 먼저 확인한다.
브라우저로 임의로 결제 저장소를 지우거나 상태를 주입해서 통과한 것으로 기록하지 않는다.

| 흐름 | 합격 조건 |
| --- | --- |
| 숙박/대실 → 객실 → 돌아가기 | 공백 화면 없이 이전 단계와 선택 상태가 일관됨 |
| 객실 변경 → 확인 → 결제수단 변경 | 선택 객실·금액이 갱신되고 이전 거래가 섞이지 않음 |
| 예약 없음 / 조회 서버 오류 | 서로 다른 안내와 적절한 재시도 경로 |
| 카드 단말기 미연결 / 승인 전 취소 | 승인되지 않았음이 확인된 경우에만 안전한 재시도·이탈 허용 |
| 현금 0원, 수납기 활성화 시도 전 취소 | 존재하지 않는 환불 작업 때문에 화면이 잠기지 않음 |
| 저장 결과 202 또는 응답 유실 | 완료·객실 비밀번호 공개 금지, 같은 요청 재확인, 새 결제 금지 |
| 돈 처리 중 무입력·화면 변경·업데이트 | 거래가 지워지거나 설치가 시작되지 않음 |

미리보기에 없는 실제 단말기·환불·인쇄·운영 예약 저장은 **미검증**으로 기록한다.
자동 테스트 개수, 명령 종료코드, 실제 확인한 화면, 차단된 항목을 별도로 남긴다.

## 예약·결제 복구 계약

- 현장 예약은 동일 결제 또는 현금 `requestId`에 묶인 `kiosk_bookings` 기록을 사용한다. 다른 내용으로 재사용할 수 없다.
- `kiosk_room_claims`는 같은 객실의 동시 키오스크 판매를 막는다. 완료 후에는 퇴실 예정 시각 + 기존 PMS의 청소 여유 2시간까지 유지한다.
- 저장 결과가 불명확한 예약은 자동 만료·재판매하지 않는다. 관리자 확인이 필요하다.
- Sheets 응답 유실은 예약 ID와 원래 행 전체가 정확히 일치할 때만 복구한다. 행을 다시 추가하지 않는다.
- 객실 상태·명령 큐·완료 기록은 하나의 Firebase 다중 경로 쓰기로 반영한다. 뒤늦은 응답은 이미 완료한 상태를 되돌리지 않는다.
- 기존 예약 체크인은 `kiosk_checkins`에 보존하고 같은 예약의 중복 체크인 명령을 막는다.
- 유효한 입퇴실 기간만 체크인할 수 있다. 퇴실 예정 시각 이후에는 기존 완료 예약이나 현장 예약 완료 캐시에서도 비밀번호를 다시 공개하지 않는다.
- PMS가 `beach_room_status`를 덮어써도 위 기록은 유지된다. 로컬 PC가 명령을 삭제했더라도 재확인으로 명령을 재생성하지 않는다.
- API 성공은 예약 저장과 해당 서버 작업의 반영을 뜻한다. 로컬 PC가 실제 문·전원·에어컨 명령을 실행했다는 보장은 아니다.
- 다른 PMS 판매 채널은 이 키오스크 객실 잠금을 사용하지 않을 수 있다. 조회된 예약과의 시간 겹침은 검사하지만, 모든 판매 채널을 묶는 전역 원자적 객실 배정은 이 변경의 범위가 아니다.

## 미확정 결제 발생 시 운영자 대응

1. 고객에게 재결제하지 않도록 안내한다. 해당 키오스크의 다음 결제는 잠금 상태로 둔다.
2. 화면의 요청/예약 ID, 단말기 승인·취소 영수증, 투입·반환 현금과 발생 시각을 확인한다. 고객 개인정보·서명 증빙을 공개 로그에 올리지 않는다.
3. 서버 예약 확인 버튼이 제공되면 같은 요청을 재확인한다. 새 요청 ID로 다시 예약하지 않는다.
4. 응답이 계속 불명확하면 운영자가 실제 결제, Sheets 예약 행, 결제 사용 기록, 객실 상태, 로컬 PC 처리 상태를 함께 확인한다.
5. 실제 처리 결과를 확정한 뒤 권한 있는 운영자가 필요한 정정·환불을 수행한다. 이 버전에는 미확정 거래를 임의 해제하는 자동 관리 도구가 없다.

브라우저 데이터 삭제, PC 재등록, Firebase 기록 삭제로 잠금만 해제하지 않는다. 이미 반환됐을 가능성이 있는 현금을 자동으로 다시 반환하지 않는다.
현금 반환 실패·부분 반환·지원하지 않는 잔액, 단말기 응답 유실·승인 금액 불일치는 관리자 확인 대상이다.
금액 불일치 시 받은 승인 증빙과 기대 금액도 보존한다. 저장 실패 자체도 안전 잠금 사유다.

카드 취소는 원래 승인 증빙이 아니라 해당 결제·금액에 연결된 별도의 실제 취소 증빙을 요구한다.
취소 성공 후 서버 기록만 실패했다면 취소 증빙으로 기록만 재시도하고 실제 단말기 취소를 반복하지 않는다.
카드 취소 기록은 예약 취소나 객실 판매 가능 상태로의 변경을 자동 수행하지 않는다. 관련 예약과 객실은 별도로 확인한다.
조기 퇴실·운영자 객실 변경 시에도 남아 있는 객실 잠금과 예약 상태를 함께 검토해야 한다.

## 현장·릴리스 합격 조건

별도 승인 후 비영업 시간에 실제 대상 PC와 장비로 수행한다. 개발 PC 모의 검사를 실기기 검사로 대신 기록하지 않는다.

- Windows 10 Enterprise 2016 LTSB 32비트 대상 PC 및 64비트 대상 PC의 설치·첫 실행·동 설정·터치 화면.
- property3 A동/B동 각각 판매·조회·체크인이 자기 동으로 제한되는지 확인.
- 승인된 테스트 예약으로 대실/숙박 결제, 예약 행·PMS 객실·로컬 PC 처리의 실제 결과 확인.
- 카드 승인·승인 전 취소·승인 후 취소, 현금 수납·정상 반환·반환 실패 및 종이 영수증.
- 네트워크 단절·재연결, 앱/PC 재시작 후 거래 복구와 설정 유지.
- 결제·체크인·인쇄·미확정 거래 중 업데이트 보류, 정상 대기 상태에서 업데이트, 재부팅 후 실행.
- ia32/x64 두 설치파일·서명·해시·전용 업데이트 DB 등록 및 올바른 비트수 선택.

각 결과에는 버전, 커밋, OS/비트수, 장비 모델, 시각, 증거와 미검증 항목을 기록한다.
치명적 실패가 있거나 결제/객실 처리 결과가 불명확하면 무인 운영과 배포를 보류한다.

# 현금 통신 기록과 무현금 점검 (1.3.9)

## 이번 변경의 범위

현금 수납 후 초기화(`RST`)와 투입 중지(`SC 0x1C`) 응답 확인 중 어느 단계가
실패했는지 오류 사유에 `[RESET]` 또는 `[STOP]`을 남긴다. 기존 3초 제한과
실패 시 입실 중단, 현금 기록 보존을 유지한다. 확인 없이 체크인하거나 자동 재결제하지 않는다.
이 변경은 과거 오류의 원인을 확정하거나 실물 장비의 수납·입실 성공을 보장하지 않는다.

1.3.9는 결제 완료/취소의 초기화 응답 후 3.5초 안정화 시간을 두고, 실제 상태 조회(`GA`)에서
대기(`0x01`) 또는 수취 준비(`0x02`)가 확인된 뒤 투입 중지를 보낸다. 준비 상태는 최대 3번
조회하며 각 응답 제한은 3초, 재조회 간격은 0.5초다. 장비 오류/준비 미확인 시 `[RESET]`으로
중단한다. 정지 명령의 정상 응답도 여전히 별도로 확인하며 초기화·정지·반환을 자동 재전송하지 않는다.
3.5초는 D동에서 약 3초 뒤 정지 응답이 회복된 기록에 여유를 둔 값이며 제조사 보장 시간이 아니다.
ONEPLUS 개별 장비는 앱 시작·장비 오류 후 첫 화면에서 대기 상태(`GA`)를 먼저 확인한 뒤 `RST → 3.5초 → GA 준비 확인 → SC 0x1C 정지 확인` 순서를 사용한다. 지폐가 처리 중이면 초기화하지 않으며, 오류가 남으면 첫 화면에서 60초마다 재시도한다. 잔돈 배출기는 대기 상태 확인 후 init·status를 실행한다. 배출·지폐 반환 명령은 자동 초기화에 포함되지 않는다. 통합 보드의 별도 순서는 아래와 같다.
현장에서 `RST → 안정화 → GA 대기 응답 → SC 정상 응답` 순서를 검증해야 한다.
아래의 개별 진단 버튼은 원래 명령 응답 시간을 측정하며, 결제의 준비 확인 전체를 대신하지 않는다.

## 기록 위치

같은 Windows 사용자의 앱 userData 폴더 아래 `logs/cash-device.jsonl`에 기록한다.
관리자 모드의 **현금 통신 점검 → 기록 읽기**에서 실제 경로와 최근 200개 기록을 확인한다.
파일은 5MB마다 순환 보관하며 현재 파일과 이전 3개를 유지한다. 가장 최근 실패 시점의
기록은 같은 폴더의 `cash-last-failure.jsonl`에도 남긴다. 앱 재시작으로 파일이 지워지지 않는다.

- `renderer`: 화면의 명령 시작·결과, 전송 시각, 소요 시간, 정상·거부·시간초과·전송실패·중복 대기.
- `bridge`: 화면과 장비 서버 사이의 명령·응답·연결 변경.
- `serial`: ONEPLUS 인식기, 캠프 BAC-2400, B동 ONEPLUS MULTI3400 보드의 COM 송수신 바이트, 원래 로그의 PC 시각(`serialAt`), 고정된 연결·읽기·쓰기 오류 코드.
- `diagnostic`: 관리자 무현금 점검 명령과 응답 결과.

고객 이름·전화번호·예약 본문·카드 승인 정보·비밀번호·프린터 내용·임의 오류 원문은 저장하지 않는다.
property4·property3 B동의 통합 보드도 serial 기록 대상이다. 캠프 `board_info`에는 허용한 `0x14` / `0x1B`
응답 필드만 기록하며 `version=null`, `versionVerified=false`로 남긴다. B동은 `0x13` 필드와
체크섬을 검증한 응답 [17]의 버전을 `versionVerified=true`로 남긴다.
로그 저장 실패가 결제 처리 결과를 바꾸지 않도록 하지만, 기록을 보존할 수 없는 새 점검은 차단한다.
상세 로그의 클라우드 업로드와 원격 명령 실행 기능은 포함하지 않는다.

## D동 현장 점검

1. 기존 수납 건의 입실/환불을 처리하고 고객이 사용하지 않는 시간에 관리자 모드로 진입한다.
2. **현금 통신 점검**에서 기존 관리자 비밀번호를 입력한다.
3. 진행 중인 거래와 인식기 안에 처리 중인 지폐가 없음을 확인한다.
4. **초기화 응답 점검**을 한 번 누르고 8초 관찰이 끝날 때까지 기다린다.
5. **투입 중지 응답 점검**을 한 번 누르고 결과와 로그를 확인한다.
6. 결과와 해당 시각의 `cash-device.jsonl`, 필요하면 `cash-last-failure.jsonl`을 보관한다.

남은 결제 저널은 비활성/손상 상태라도 삭제하지 않고 점검을 거부한다. 다른 IPC/예약/결제 작업 및
업데이트와 겹치지 않게 실행한다. 점검 중 지폐 수취·배출·예약 요청을 보내지 않는다.
다른 장비 진단 탭의 수취/반환 버튼을 대신 누르지 않는다.

## 결과 해석

| 결과 | 의미 |
| --- | --- |
| 정상 응답 | 해당 명령의 OK를 3초 미만에 수신 |
| 장비 거부 응답 | NG를 수신. 포트가 끊겼다고 단정하지 말고 명령/장비 규격 확인 |
| 3초 제한 이후 응답 | 통상 결제 제한을 넘긴 지연 응답 |
| 8초 동안 응답 없음 | 관찰 구간의 무응답. 장비/배선/전원/명령 규격 추가 확인 |
| 전송 실패 또는 읽기·쓰기 오류 | 연결 경로와 COM 포트 확인 |
| serial에서는 수신했지만 bridge/renderer에 없거나 늦음 | 장비 서버 파싱 또는 앱 내부 전달 단계 확인 |

각 점검은 한 명령만 전송하고 관찰 기간 내 잠금을 유지한다. 정상·거부 응답을 빨리 받아도
8초가 끝난 후 다음 점검을 허용해 뒤늦은 응답과 다음 명령이 겹치는 것을 줄인다.
프로토콜에 거래별 응답 ID가 없으므로 관찰 창 밖의 임의로 늦은 응답까지 식별하는 보장은 없다.
무현금 점검 결과만으로 실제 현금 결제·거스름돈·체크인 전체 검증을 완료 처리하지 않는다.

## 비치 B동 ONEPLUS MULTI3400 (10차 소스 수정, 현장 앱 미검증)

B동은 `property3 + KIOSK_BUILDING=B`에서만 `multi3400.py`를 선택한다. 포트는
`BAC2400_PORT` → `BOARD3400_PORT` → COM5, 9600 8N1이다. 외부기기 등록에는
**ONEPLUS MULTI3400 통합 보드**와 `MULTI3400_BD1_VALUE`(기본 10000원)를 표시한다.
캠프의 BAC-2400 9600 8E1/TLV 구현은 별개다. B동에 캠프 TX를 보내지 않는다.

제조사 `Multi3400_V1_1.utf8.cpp:645–665`, `Multi3400_V1_5.utf8.cpp:652–672`의
`TXData_DisplayMSG`는 [0..12] XOR를 [13]에 넣고 **14바이트**를 전송한다.
두 데모의 호출 인자도 14이며 [1]=13이다. `RS232.cpp`는 8 data bits, NOPARITY, ONESTOPBIT다.
캡처에 15토큰처럼 보인 TX는 15바이트 송신의 근거가 아니다. 상태 RX는 19바이트, [1]=18,
[18]=XOR([0..17])다. 0x16/0x17/0x18 응답의 2바이트 big-endian 카운터를 0x13 상태 매수로 읽지 않는다.

데모와 앱을 동시에 같은 COM에 연결하지 않는다. 아래 명령은 제조사 데모와의 대조용이며
실장비에서 앱으로 실행한 결과가 아니다. 현금 시험은 승인된 시험 예약에서만 한다.

| 기능 | TX (14바이트, 최대 투입금 0 예시) | 필요한 증거 |
| --- | --- | --- |
| 상태·IO 버전 조회 | `FE 0D 11 00 00 00 00 00 00 00 00 00 00 E2` | 19바이트 0x13, 유효 XOR, [17]=버전 |
| 데모 BV1+BV2+Coin ON 대조 | `FE 0D 10 07 00 00 00 00 00 00 00 00 00 E4` | ACK 11; 앱은 동전을 켜지 않음 |
| BV1+BV2 허용, Coin OFF | `FE 0D 10 03 00 00 00 00 00 00 00 00 00 E0` | ACK 뒤 새 0x13에서 [3]&7=3 |
| 최초 결제 투입금 Clear, 모두 OFF | `FE 0D 10 08 00 00 00 00 00 00 00 00 00 EB` | ACK 뒤 투입 6개 매수=0, BV/Coin OFF |
| 투입 중지 | `FE 0D 10 00 00 00 00 00 00 00 00 00 00 E3` | ACK 뒤 [3]&7=0, BV Busy 해제; ACK 단독은 정지 아님 |
| BD1 Reset, 모두 OFF | `FE 0D 10 00 02 00 00 00 00 00 00 00 00 E1` | ACK 뒤 새 정지·BD1 정상 상태, 현금 방출 0회 |
| BD1 1장 지급 (시험만) | `FE 0D 12 00 00 01 00 00 00 00 00 00 00 E0` | 새 [13] 증가=1, [3]&8=0, [4]&0x11=0, 실물 단가/매수 일치 |

실제 결제 제어는 [7]에 결제액/1000 올림(1~255)을 넣고 XOR를 다시 계산한다.
예: 60000원 Clear `FE 0D 10 08 00 00 00 3C 00 00 00 00 00 D7`,
허용 `FE 0D 10 03 00 00 00 3C 00 00 00 00 00 DC`.
255000원 초과는 0(무제한)이며 `input_limit_unavailable`을 남긴다. 데모와 최대 투입금의
물리적 과투입 제한 효과를 확인한다. 중지·리셋은 투입/방출 카운터를 Clear하지 않는다.

현장 RX `FE 12 13 47 11 00 00 00 00 00 01 00 00 00 00 00 00 12 BA`는
BV1/BV2/Coin ON, HP1 Err, BD1 Err, BD1 Empty, 5만원 1장, IO 버전 **0x12**다.
첫 연결의 기존 매수는 새 결제로 적립하지 않는다. 이후 매수 증가분은 1천/5천/1만/5만원을
각각 bill code 01/05/0A/32로 전달하고 렌더러가 전부 기록한다. 투입 중지를 확인해 추가 수납을
막은 뒤 수납 큐 전체를 기록하고 완료 판단한다. 중지가 실패해도 읽은 수납액은 먼저 기록한다.
결제 중 재허용 때 Clear하지 않는다.
물리적 권종 거부 명령이 없으므로 작은 지폐도 수납액이다. 단가 배수가 아닌 거스름돈/취소액은
새 지급을 시작하지 않고 PMS 사고 기록과 첫 화면 복귀 경로로 처리한다.

자동 복구는 새 상태 → 필요하면 모두 OFF → ACK/정지 재확인 → BD1 Reset → ACK/새 상태 확인이다.
방출·반환·수취 허용·카운터 Clear는 0회다. 지급 증거 불충분/오류/Empty/타임아웃은
`payout_uncertain` 잠금이며 자동 재시도/리셋하지 않는다. 지급 전체 제한 9초, 수취 제어 2.5초,
복구 6초이며 고객 화면의 기존 제한 시간 및 PMS 복구 경로를 유지한다.
프레임 하나씩 응답을 기다리고 250ms 주기로 조회한다. 응답 ID가 없으므로 임의의 장시간 지연/카운터
재시작·wrap은 성공 증거가 아니며, 카운터 감소는 `counter_discontinuity`로 수취 허용을 차단한다.

`cash-device.jsonl`에는 MULTI3400 TX/RX, `multi3400-fe`/`0x13` 원문 필드, 실제 [17] 버전을 남긴다.
9차의 `source=adapter|board_status|board_ng`, target/reason 체계를 유지한다. 주요 추가 원인은
`board_nak`, `invalid_length`, `invalid_checksum`, `unexpected_response`, `response_timeout`,
`dispenser_empty`, `payout_count_mismatch`, `counter_discontinuity`다. `acceptor_stop_unconfirmed`는
ACK 뒤 실제 정지를 확인하지 못했을 때 기존 PMS 차단 의미를 유지한다.

## 캠프 BAC-2400 통합 보드 (기존 경로)

- 선택: 캠프 `property4`에서만 BAC-2400 TLV 어댑터를 사용한다.
- 캠프 외부기기 등록에는 인식기/방출기별 포트 대신 **BAC-2400 통합 보드** 하나를
  등록한다. `.env.local` 설정은 `BAC2400_PORT`, 이전 호환 이름은 `BOARD3400_PORT`다.
- 기존 캠프 초기화도 GA/RST/SC/I를 BAC 명령으로 번역했다. 지급/반환 명령이 나가던 것은
  아니지만, RST/I/SC의 성공을 보드 응답 없이 시리얼 쓰기만으로 만들던 문제가 있었다.
  수정 소스는 자동 복구에서 ONEPLUS 패킷을 쓰지 않고 `cash_board_recover`로 분기한다.
- 인식기: 새 상태·권종 수량 조회 → 대기 확인 → 투입 중지(수량 초기화 없음) → 새 정지 상태 확인.
  방출기: 새 수량·상태·가동 조회 → 대기 확인 → BD1 리셋 → 새 대기·0 카운터 확인.
  자동 복구에는 수취 활성화·지급·지폐 반환이 없으며, 미확정 지급 흔적이 있으면 리셋하지 않는다.
- 부분 응답·미지 상태·처리 중이면 해당 기기만 `needs_attention`으로 남긴다. Python 복구는
  6초, Electron 대기는 9초 이내 종료하며 거래가 없는 첫 화면에서 제한된 재시도를 한다.
- 결제/무현금 점검의 RST/SC도 새 상태가 맞아야 OK를 만든다. 성공은 시리얼 전송 성공과 다르다.

### 제조사 데모와 대조할 명령 및 응답

현재 코드의 9600 8E1과 아래 바이트를 데모 통신 기록/제조사 규격과 대조한다. 실장비에서 실행한
기록이 아니며, 현금·예약 테스트는 승인된 시험 건에서만 한다. 데모와 앱이 같은 COM을 동시에 열면 안 된다.

| 기능 | 코드가 보내는 바이트 | 확인할 응답/효과 |
| --- | --- | --- |
| BV1 조회 | `59 A6` | TLV `0x18` 정확히 4바이트 권종 수량, `0x1B` 정확히 3바이트 상태 |
| BV1 정지 (자동 복구) | `5B A4 03 10 00 00 13` | enabled/processing가 꺼진 새 상태, 권종 수량 보존 |
| BV1 초기화 (결제/개별 점검 RST) | `5B A4 03 10 02 00 11` | 수량 0 및 정지 상태; 읽지 않은 수납이 있으면 전송 차단 |
| BV1 수취 준비 (결제만) | `5B A4 03 10 03 00 10` | 새 수량 0 및 enabled 상태, 1천원/5천원 물리적 거부 설정 |
| BD1 조회 | `71 8E` | 같은 응답에 `0x15` 4바이트 수량, `0x16` 4바이트 상태, `0x17` 1바이트 가동 |
| BD1 리셋 (자동 복구) | `73 8C 05 01 00 00 01 00 05` | 실제 리셋 의미, 지급 0회, 새 대기·BD1 수량 0 |
| BD1 1장 지급 (승인된 시험만) | `73 8C 05 00 00 00 01 00 04` | BD1 인덱스 2, 회차 수량 0→1, 오류 없음·가동 종료·실물 1만원 1장 |
| BAC-2400 보드 버전 조회 | 규격 미확보로 전송 안 함 | B동 MULTI3400의 버전 바이트를 BAC 버전으로 혼용하지 않음 |

`0x1B`의 뒤쪽 바이트나 `0x14`를 제조사 설명 없이 버전으로 해석하지 않는다. 알 수 없는
상태 비트(예: `0x11`)를 대기로 간주하지 않는다. MULTI3400은 `FE` 프레임/9600 8N1이므로
이름이 비슷하다는 이유로 혼용하지 않는다. 캠프의 `FE` 응답은 미지원으로 기록하고 성공 응답을 만들지 않는다.
BD1 수량이 누적인지 회차별인지 구분할 증거가 없으면 지급 성공을 만들지 않는다. 완료에는
이번 회차의 0 카운터·변화·정확한 요청 수량·새 정상 상태·가동 종료가 모두 필요하다.
부분 지급·지급 후 시간초과·부분 시리얼 쓰기는 미확정 흔적으로 잠그고 자동 지급/리셋을 하지 않는다.
지급의 조회·배출 전체 제한은 9초이며, 화면의 10초 대기가 끝난 뒤 늦은 조회 응답으로 지급을 시작하지 않는다.
장비 서버 재시작 뒤 물리적 상태만으로 과거 지급 결과를 확정하지 않으며 기존 결제 저널/PMS 사고 기록을 보존한다.
